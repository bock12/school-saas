# TASK-0004 — Unified API Route Authorization Guard

**Status:** APPROVED · **Priority:** Critical · **Owner:** ChatGPT / Architecture & Security Supervision · **Target:** Gemini / Antigravity
**Task Type:** Application security foundation
**Implementation:** Allowed
**Database / Schema / Migration changes:** Prohibited
**RLS changes:** Prohibited
**Dependency changes:** Prohibited
**Infrastructure changes:** Prohibited

## Objective
Create a centralized, request-safe authorization boundary for Next.js Route Handlers so privileged API routes can consistently authenticate the caller, establish trusted tenant context, enforce role/permission requirements, and return standardized JSON authorization failures before any privileged database client is created or used.

## Required Design
Create `src/lib/auth/api-guard.ts` with an API-safe authorization contract. It must:
- authenticate the request using the server-side Supabase client and the current session/user;
- fail closed when authentication cannot be established;
- resolve tenant context from trusted server-side membership/profile data, never from an unverified caller-supplied slug or header;
- support explicit allowed roles/permissions;
- support platform-level `super_admin` authorization only where explicitly requested by the caller's options;
- provide standardized JSON 401/403 responses suitable for Route Handlers and never use `redirect()`;
- expose enough verified actor context for downstream handlers to perform resource/object authorization;
- avoid creating or returning a service-role client as proof of authorization;
- ensure privileged-client creation remains a downstream operation after authorization succeeds.

## Scope
Primary implementation file:
- `src/lib/auth/api-guard.ts`

Supporting files may be modified only when required to make the guard compile or integrate safely with existing server-auth primitives. Do not refactor vulnerable API routes under this task except for minimal type/import compatibility if absolutely necessary; route containment belongs to TASK-0005.

## Security Invariants
1. No anonymous request may receive an authorized result.
2. Missing, invalid, inactive, or ambiguous tenant context must fail closed.
3. Caller-supplied `tenantSlug`, `tenantId`, or `x-tenant-slug` cannot override verified membership.
4. Role checks must be explicit and deny by default.
5. Object/resource authorization remains a separate downstream check; the guard must not imply object ownership merely because the caller is authenticated.
6. The guard must not instantiate `createAdminClient()` before authorization succeeds.
7. The guard must not expose service-role credentials or sensitive profile fields in its response.
8. API failures must use HTTP JSON responses, not page redirects.
9. Existing page/server-action guards using `redirect()` must remain behaviorally unchanged.

## Acceptance Criteria
- **AC-001:** `src/lib/auth/api-guard.ts` exists and exports a documented `authorizeApiRequest` API.
- **AC-002:** Unauthenticated requests produce a standardized HTTP 401 JSON response.
- **AC-003:** Authenticated users with inactive/missing/invalid tenant membership fail closed.
- **AC-004:** Allowed-role/permission checks produce HTTP 403 JSON responses when the caller lacks authorization.
- **AC-005:** Verified tenant context is derived from trusted server-side data and cannot be replaced by arbitrary request headers/query parameters.
- **AC-006:** The guard does not use `redirect()` or page-only authorization helpers.
- **AC-007:** No service-role/admin client is instantiated by the guard before authentication, tenant, and role authorization succeeds.
- **AC-008:** The returned authorized context contains only the minimum verified actor/tenant information required by downstream API handlers.
- **AC-009:** Existing application build/type checks pass after implementation.
- **AC-010:** Automated tests are added only if an existing test framework can support them without adding dependencies; otherwise record the test gap and leave test-framework installation to TASK-0008.
- **AC-011:** No database schema, migration, RLS, dependency, infrastructure, or unrelated route behavior is changed.
