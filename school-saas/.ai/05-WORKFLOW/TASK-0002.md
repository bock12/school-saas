## 1. Objective
Eliminate credential and secret exposure risks across the repository without modifying production secrets, rewriting git history, or breaking core application functionality. Secure database pool connections with verified TLS, restrict privileged administrative clients to server-side execution, eliminate unsafe raw SQL manipulations of `auth.users`, and provide regression testing for previous security boundaries.

---

## 2. Invariants & Acceptance Criteria
- **AC-001 (Zero Tracked Production Credentials):** No active or historical plaintext database credentials, Supabase pooler connection strings, or service-role keys may remain in the tracked working tree.
- **AC-002 (Elimination of Ad-Hoc Migration & Debug Scripts):** Remove all unvetted root and debug scripts containing hardcoded credentials or dangerous database operations (`run_migration_*.js`, `test-create-session.ts`, `dump_applicants.js`, `src/scripts/*`).
- **AC-003 (Untracking of Scratch Artifacts):** Untrack `scratch/` directory, purge committed temporary scripts, and configure `.gitignore` to prevent future tracking.
- **AC-004 (Sanitized Maintenance Scripts):** Utility and diagnostic scripts under `scripts/` must source credentials from environment variables (`DATABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`) and must never log plaintext credentials.
- **AC-005 (Secure Database TLS Enforcement):** All PostgreSQL connections across `src/` and `scripts/` must enforce secure TLS validation (`rejectUnauthorized: true`). `rejectUnauthorized: false` is forbidden.
- **AC-006 (Fail-Closed Environment Configuration):** Environment variables required for privileged operations must be strictly validated; missing configurations must throw clear errors rather than falling back to default credentials.
- **AC-007 (Server-Only Administrative Isolation):** `src/lib/supabase/admin.ts` and `src/lib/db/pg-fallback.ts` must enforce server-only isolation via `import 'server-only'` to prevent bundling into client components.
- **AC-008 (Elimination of Raw auth.users SQL Mutations):** Direct SQL insertions, updates, or password overrides targeting `auth.users` must be completely removed in favor of Supabase Auth Admin APIs.
- **AC-009 (Automated Security Test Suite):** A dedicated regression suite `tests/security/credential-containment.test.ts` (SEC-01 through SEC-18) must validate security properties across the repository.
- **AC-010 (Admin Client Integrity):** Verify `src/lib/supabase/admin.ts` is server-only, fail-closed, and cannot expose the Supabase service-role credential to client code.
- **AC-011 (Service-Role Import Audit):** Enumerate every `createAdminClient`, `SUPABASE_SERVICE_ROLE_KEY`, and `DATABASE_URL` consumer in the repository and classify each as server-safe or requiring remediation.
- **AC-012 (No Unnecessary PostgreSQL Fallback):** Removing raw `auth.users` password manipulation must not introduce unnecessary `getPgPool()` usage. Remove dangerous login mutations without adding new direct-database dependencies.
- **AC-013 (Authentication Flow Integrity):** Registration, login, provisioning, password reset, and profile synchronization must use Supabase Auth APIs for authentication state. Profile synchronization on auth callback must never trust user-controlled `user_metadata.role` or `user_metadata.tenant_id` as authoritative data. No route may directly manipulate `auth.users` credentials via SQL.
- **AC-014 (Historical Secret Distinction):** The implementation report must distinguish: (1) current-tree remediation, (2) exposed Git history, (3) credential rotation, and (4) deployment-secret replacement.
- **AC-015 (Static Security Tests):** Tests SEC-01 through SEC-18 must test concrete security properties rather than superficial keyword matching.
- **AC-016 (RLS Preservation):** Do not weaken or bypass existing RLS policies to make credential/authentication changes work.
- **AC-017 (Previous-Task Regression):** Verify TASK-0004 `authorizeApiRequest()` and TASK-0005 privileged API containment continue to function after TASK-0002 changes.
